1How to use this document

The handover PDF explains why this project is the way it is. This one explains where things are. It is written to be open on a second screen while someone asks questions about the code, so every claim in it carries a file and, where it helps, a line number.

Line numbers were correct when this was generated and drift as the code changes. Treat them as "near the top" / "about two thirds down" rather than as exact addresses, and use the symbol names, which do not move.

The eight files that matter most

Eighty source files and twenty-one test files, and this is where the substance is. If someone reads nothing else, read these.

File Why it matters
scan/runner.ts Scan orchestration, and the one design commitment that shapes the whole product: a scan does not fail, it reports per-unit outcomes.
scan/pipeline.ts Where raw AWS JSON becomes verdicts. Every security fact in the product is computed here, over the whole estate at once, never by the model.
scan/analysers/publicAccess.ts The best single example of why the model is not allowed to answer: four inputs interact, and three of them can cancel a fourth.
db/queries.ts The curated query library — thirteen hand-written Cypher queries that are the only questions the agent can ask.
agent/tools.ts The tool boundary: sixteen parameterised tools over those queries. The model picks and fills in arguments; it never writes a query.
agent/citations.ts Every ARN in an answer is checked against what the tools actually returned. This is the answer to "why should we trust it".
infra/readonly-role.yaml The replacement read-only role: SecurityAudit + ViewOnlyAccess, an explicit deny on data-plane reads, trust scoped to one principal with an external id.
packages/mock-aws/src/topology.ts The hand-written answer key. Ground-truth tests grade the scanner against this, so an analyser bug cannot mark its own homework.

Reading orders

Ten minutes

packages/shared/src/model.ts (what a resource is) → scan/runner.ts (how one is found) → scan/pipeline.ts (how it gets a verdict) → agent/tools.ts (what the model may ask).

An hour

The four traces in sections 3–6, in order, with the files open. They cover every layer and cross every boundary in the system, which no single file does.

The one-sentence architecture

The scanner reads AWS and writes Postgres; Postgres is the system of record and the history; Neo4j is a projection rebuilt from it; the agent reads only Neo4j, only through curated tools; the UI reads the API and never AWS.

Why the boundaries fall where they do

packages/shared exists so the model cannot drift. A resource kind is one as const array; adding a kind without handling it in the graph projection or the UI colour map is a type error rather than a runtime surprise.

aws/ is separate from scan/ because one is about how we talk to AWS (assume-role, retries, endpoints, region discovery) and the other is about what we ask it. The only difference between scanning the mock and scanning a real account lives in aws/clients.ts — an endpoint override — which is why the same scanner code is exercised by both.

Collectors never interpret. A collector returns resources and the relationships it can see locally. Anything that needs two resources to be true at once — "this instance is exposed", "this role is admin", "this volume is idle" — is computed later, in scan/pipeline.ts, over the whole estate. That split is why a security verdict can be unit-tested without AWS, a database, or a network.

db/queries.ts is the agent's only vocabulary. The agent directory holds no Cypher except the guarded escape hatch. Someone reviewing what the agent can possibly do reads one file.

packages/mock-aws is a workspace, not a fixture directory, because the seeder builds the account through the real AWS SDK against moto. The resources the scanner later discovers were produced by the same API surface AWS would produce, not hand-written JSON that happens to match what the code expects.

Where the mock boundary actually is

Exactly one place: aws/clients.ts sets an endpoint override and static credentials when AWS_MODE=mock. Every other file — collectors, analysers, pipeline, repository, projection — is identical in both modes and untestable against one but not the other. The scanner cannot tell the difference, which is the point.

3Trace: a scan, end to end

Triggered by npm run scan or by POST /api/scans from the UI. The two entry points do the same work in the same order; the route additionally streams progress.

cli/scan.ts:26 · routes/scans.ts:75
Entry. migrate() first, so the schema exists, then runScan(). The route creates the scan row and opens a server-sent event stream before doing any work, so the UI can show progress from the first unit.
scan/runner.ts:102 → aws/credentials.ts:107
getSession() assumes the customer role with an external id and caches the credentials until they are near expiry. Concurrent callers during a refresh share one in-flight AssumeRole rather than stampeding STS — a scan fans out across every region at once and they all miss the cache in the same millisecond. This is where the account id comes from — it is read from the assumed session, never from configuration, which is what stops a mock scan being labelled with a real account's number.
aws/regions.ts
Region discovery via DescribeRegions, filtered to what is actually enabled, intersected with AWS_SCAN_REGIONS when set. Guessing regions wastes an API call per service per region and still misses the one the customer actually uses.
scan/runner.ts:128
The unit list is built: one (service, region) pair per regional service, one global unit for IAM and S3. Six services over three regions is fourteen units.
scan/runner.ts:197 → scan/limiter.ts:12
runWithConcurrency(tasks, SCAN_CONCURRENCY). Unbounded fan-out on a real account is a few hundred simultaneous AWS calls and guaranteed throttling. Thirty lines: a fixed pool of workers pulling from a shared index, and no rejection handling, because a failed unit is an outcome rather than a thrown error.
scan/runner.ts:175 → scan/collectors/*.ts
Each unit calls one collector. Each returns resources plus the relationships visible locally. A collector that throws fails its own unit only: explainFailure() at line 71 turns the SDK error into something a user can act on (AccessDenied becomes "Not permitted to read rds in eu-west-1. The role is missing a Describe/List permission for this service."), and the scan continues.
scan/runner.ts:200 → scan/pipeline.ts:64
annotate() runs once over the merged estate: synthetic Account, Region and Internet nodes, then the four analysers in order — admin (line 117), public access (123), idle (142), reachability (145).
db/repository.ts:45
saveScanResult() writes units, resource snapshots and relationship snapshots in one transaction. All or nothing: a half-written scan would be worse than no scan, because it would read as complete.
db/neo4j.ts:139
projectGraph() rebuilds the graph wholesale from that scan's snapshots, inside one transaction. Postgres is written first deliberately: if the projection fails the scan is still durable and can be re-projected without going back to AWS.

The question this trace answers

"What happens if one region is throttled or one permission is missing?" Nothing fails. The unit fails, the banner names it, the other thirteen units still produce a graph, and the scan is recorded as partial rather than succeeded — computed by rollUpStatus() in packages/shared/src/scan.ts, which has its own tests.

4Trace: a question, end to end

"Which S3 buckets are public?" typed into the chat panel. This is the path most worth being able to narrate, because every AI-engineering decision in the project is visible along it.

web/components/Chat.tsx:88 → web/src/api.ts:203
POST /api/chat over fetch, reading a server-sent event stream from the response body. Not EventSource, which cannot send a request body — noted in web/src/api.ts where the reader lives.
routes/chat.ts:29
Opens the stream, then calls ask() with an emit callback. Every event the agent produces is forwarded to the browser as it happens; the final message is also persisted to the messages table.
agent/agent.ts:80
ask(). First it loads the latest scan and an account summary and puts them in the system prompt, so the model knows when the data is from and how big the account is before it calls anything.
agent/agent.ts:116
The loop, capped at MAX_ITERATIONS: stream a model turn, collect tool-use blocks, run them, hand the results back, repeat until the model answers in prose. Text blocks emitted during tool-calling turns become agent.thinking events rather than being dropped.
agent/tools.ts:273
runTool() dispatches by name to one curated query — find_public_resources → q.findPublicResources(). Sixteen cases, one graph_query escape hatch. The model chose the tool and the arguments; it did not write the query.
db/queries.ts:88
Hand-written Cypher, run in a Neo4j read transaction. It matches on isPublic = true — a property computed during the scan — and returns the publicReason alongside it, so the answer can quote evidence rather than assert a verdict.
agent/citations.ts:122
Every ARN in every tool result is recorded in a CitationTracker as the loop runs.
agent/agent.ts:231 → agent/readOnlyGuard.ts:134
enforceReadOnlyNotice(question, answer). If the question asked for a change (requestsMutation(), line 105) and the answer does not already decline (assertsReadOnly(), line 121), the refusal is prepended. It runs on the finished answer rather than short-circuiting the question, because the model's answer is usually genuinely useful — it names the resource, its state and the command an engineer would run. Only the missing sentence is added. The prompt asks for this too and the model does not reliably comply, which is exactly why it is code (ADR-009).
agent/citations.ts:59
validateCitations() extracts every ARN-shaped string from the finished answer and checks each against what the tools actually returned. Unknown ARNs are reported, not silently kept. This is the mechanism behind "how do you know it isn't making things up", and it caught a real hallucination — engineering log #32, where a tool returned paths but not the resource they started from, and the model filled the gap with a plausible truncated ARN.
agent/agent.ts:249 → Chat.tsx:113
agent.finished carries the message, its tool-call trail and its validated citations. The UI highlights every cited ARN in the graph and keeps the trail expandable under the answer.

Four guarantees along one path

The role cannot write; the scanner only calls Describe/List/Get; no tool can express a mutation; raw Cypher is lexically validated (agent/cypherGuard.ts) and run in a read transaction. Independent layers, so no single mistake removes the guarantee.

5Trace: connecting a real AWS account

The onboarding flow. Its design rule is that the product guides onboarding and never performs it: nothing here deploys a stack or writes a customer's configuration (ADR-010).

web/components/ConnectionGuide.tsx
Four steps with copyable commands. Opened from the header, and also linked from the empty state.
routes/connection.ts:243
GET /api/connection/external-id generates a per-customer external id. The customer pastes it into their own stack; it is a shared secret that prevents the confused-deputy problem, not a password.
routes/connection.ts:120 → aws/principal.ts:49
GET /api/connection reports who this backend runs as, converted for a trust policy. assumablePrincipalArn() exists because sts:GetCallerIdentity answers a different question from the one a trust policy asks: it returns the session ARN (arn:aws:sts::…:assumed-role/Role/session), and a trust policy needs the identity (arn:aws:iam::…:role/Role). The guide showed the wrong one until a real deployment failed on it.
aws/principal.ts:156
validateAssumeRoleTarget() checks the configured target is a role, because sts:AssumeRole cannot assume a user — the exact mix-up a customer makes when they paste their own identity into the scanner's configuration. It names the mistake instead of failing later with AccessDenied.
routes/connection.ts:254
POST /api/connection/test attempts the assume-role and diagnoses the failure: trust policy names a different principal, external id mismatch, role does not exist, wrong account. Each maps to a specific next action rather than echoing the SDK error.
routes/connection.ts:206
POST /api/connection/mode switches between the demo account and the real one at runtime. It does not rewrite .env, and it does not rescan — the banner says the graph still holds the previous account's data until you run one (ADR-013).

The stack the customer deploys is infra/readonly-role.yaml, and it has its own test file — infra/template.test.ts, twenty-two assertions — because the original template turned out never to have been deployed. That file checks the permission set, the explicit deny, the trust scoping, the external-id condition, and the two CloudFormation length limits that a real deployment rejected.

6Trace: a finding becomes a fix

Clicking a flagged node opens the verdict and, beside it, the exact commands that would fix it. Nothing in the product runs them (ADR-014). This trace is short but crosses three boundaries, and the last one is the interesting one.

scan/pipeline.ts:123 → analysers/publicAccess.ts
At scan time, the verdict and its reason are written onto the resource as derived.isPublic / derived.publicReason. The fix and the verdict therefore come from the same evidence, computed once.
db/neo4j.ts:139
The projection promotes derived facts to top-level node properties, and JSON-encodes nested ones. Neo4j properties must be primitives or arrays of primitives, so a public access block or a list of ingress rules is stored as a string.
routes/graph.ts:37
GET /api/resources/:arn/remediation. This route and its sibling are why maxParamLength is 2048 in app.ts: an ARN is the path parameter, and a service-linked role's ARN is 120 characters — over Fastify's default cap of 100, which returned 414 for ten of nineteen IAM roles in a real account.
remediation/fromGraph.ts:87
remediationInputFromGraph() parses those JSON-string properties back into objects, and filters incoming edges to the four that mean "in use". Parsing is best-effort by design: a property that will not parse is dropped rather than thrown on, because a 500 on a detail page is worse than one missing suggestion.
remediation/remediation.ts:529
remediationsFor(input) — one generator per finding kind, ordered public → exposed → admin → unprotected → idle. Each returns commands, a caution (a required field, not optional), a risk rating, and a read-only command to verify the fix worked.
web/components/Remediation.tsx
Rendered with a copy button and no apply button. The caution is rendered above the commands, because a warning under the thing it warns about is decoration.

The detail worth showing someone

LegacyDeployRole in the fixture is an administrator by way of an inline policy named legacy-deploy-inline — no AdministratorAccess attached. The generator selects the managed-policy detach only when a policy ARN actually matches (line 201), so for this role it emits none, and instead produces "replace the inline policy": save the current document to backup.json with get-role-policy, write a scoped replacement, then put-role-policy. The obvious detach-role-policy --policy-arn …/AdministratorAccess would have exited zero and changed nothing.

The caution is generated from the graph too: the edges into the role name what uses it, so the warning reads "legacy-image-resizer currently uses this role, and will lose every permission it grants the moment this is applied". For a user, the text deliberately says the opposite — nothing visibly using it is not evidence it is unused, because access keys live in CI pipelines and on laptops where an inventory cannot see them.

7The data model

One type definition, in packages/shared/src/model.ts, shared by the scanner, the projection, the agent's queries and the React components. Twenty node kinds and thirteen edge types (ADR-003).

Node kinds

Account · Region · Vpc · Subnet · SecurityGroup · InternetGateway · NatGateway · RouteTable · Ec2Instance · EbsVolume · ElasticIp · S3Bucket · IamRole · IamUser · IamPolicy · InstanceProfile · RdsInstance · DbSubnetGroup · LambdaFunction · Internet

Account, Region and Internet are synthetic — they are not AWS resources. Internet exists so that "what can reach the production database?" is a path query from a node rather than a special case in code.

Edge types

Edge Meaning
IN_REGION IN_VPC IN_SUBNET Containment. Cheap, and what makes region and tier questions trivial.
HAS_SECURITY_GROUP ROUTES_TO USES_SUBNET_GROUP Network structure as AWS reports it, before any interpretation.
ATTACHED_TO Volume to instance, elastic IP to instance. Absence is the idle signal.
HAS_INSTANCE_PROFILE PROVIDES_ROLE EXECUTES_AS HAS_POLICY CAN_ASSUME The identity chain. EXECUTES_AS is how a trivial Lambda turns out to be running as an administrator.
CAN_REACH Derived, not observed. Computed by analysers/reachability.ts from security group rules, subnet routing and public-accessibility flags, carrying the ports and the evidence that justified it.

Derived facts

Every verdict is a flag paired with a human-readable reason, because the agent is instructed to quote the reason — a DevOps engineer needs to be able to disagree with a finding, which means seeing the evidence.

Field Question it answers
isPublic / publicReason Reachable by an anonymous principal, or from the internet.
isUnprotected / unprotectedReason Nothing prevents this becoming public. Deliberately separate from isPublic: a bucket with Block Public Access off is not public, it has lost a guardrail (ADR-012).
isAdmin / adminReason Effective *:*, by any combination of managed and inline policy.
isIdle / idleReason / estimatedMonthlyCostUsd Provisioned, billable, structurally unused.

Postgres tables

In apps/api/src/db/schema.sql. Everything is append-only per scan — a scan never updates a previous scan's rows, which is what makes change detection answerable and lets a bad scan be discarded without corrupting history.

Table Holds
scan_runs One row per scan: account, status, regions, counts, API calls.
scan_units One row per (service, region) — the unit of partial failure, and the table the banner reads. region is 'global' rather than NULL so it can be part of the primary key.
resource_snapshots Immutable snapshot per resource per scan, with a fingerprint hash of the queryable state — so diffing two scans is an index-backed join, not a JSONB comparison across thousands of rows.
relationship_snapshots The edges as of that scan.
conversations / messages Chat history, plus the audit trail: which tools ran, which ARNs were cited, and whether any citation was unsupported. Kept out of the graph so chat volume never competes with the agent's own queries.
eval_runs Eval results over time, so a regression in answer quality is visible rather than discovered in a demo.

The sentence that answers "why two databases?"

Postgres answers "what did this account look like at 09:00, and what changed since?" — a history question, and relational storage with an immutable snapshot per scan is the right shape. Neo4j answers "what can reach the production database?" — a variable-length path question, which is three lines of Cypher and a recursive CTE nobody enjoys reviewing. The graph is disposable; it is rebuilt from Postgres, never written to directly.

8File reference — apps/api

Every non-test file, with the thing worth saying about it. Sizes are lines including the header comments, which in this codebase carry the reasoning.

src/aws/ — how we talk to AWS

File Ln What it is for
credentials.ts 143 Cross-account assume-role with an external id. dave.io never holds customer keys. Caches the session, shares one in-flight refresh between concurrent callers, and takes the account id from the assumed session rather than from configuration.
clients.ts 118 Every AWS client, built one way. retryMode: "adaptive" (client-side rate limiting on top of exponential backoff with jitter) and an API call counter. The only place that knows whether we are talking to moto or to AWS.

resourceExplorer.ts 144 The brief's suggested fast path, used as one. Needs an index that only exists if the customer created it — and a read-only role cannot create one — so SDK enumeration stays the tested default.

The two eval tiers

Tier 1 — is the data right? evals/checks.ts holds fifteen checks as data, so the same definitions run from Vitest and from the Trust panel in the product. No API key, no model, milliseconds.

Tier 2 — does the agent use it right? Twenty-one cases in evals/cases.ts, graded on cited ARNs with precision, recall and F1 rather than text similarity (evals/grade.ts). Needs a key; run with npm run evals -w @daveio/api. Current state: 21/21, mean F1 1.0.

Why grade on citations rather than wording

Citations are already validated against tool output, so they are a far stronger signal than string overlap — and they cannot be gamed by an answer that happens to use the right words. Two mustNotMention patterns were deleted during development for the opposite reason: a lexical pattern cannot test a negated claim, because "northwind-reports is not public" contains the string it was looking for.

The five things that are true about the architecture

  1. Security reasoning is computed in code, never by the model. Every verdict is a property on a node with a reason string attached, written during the scan.
  2. The agent cannot express a mutation. Not "is told not to" — cannot. Four independent layers.
  3. Postgres is the system of record; the graph is disposable. Rebuilt per scan, never written to directly.
  4. A scan does not fail. It produces per-unit outcomes, and the UI is loud about the partial case.
  5. The mock differs from a real account in exactly one place. An endpoint override in aws/clients.ts.

The honest limits, stated before anyone asks

  • Neo4j Community has no role-based access control, so a read-only database user is not available — the read transaction is the guarantee. In production: an Enterprise read-only role or a replica.
  • The projection is a whole-graph rebuild. Fine at a few thousand resources; the first thing to change for a large account is an incremental projection keyed on the fingerprints already in Postgres.
  • GET /api/graph is unpaginated. The UI filters by kind, but the API hands over the whole graph — the next thing to break after the projection.
  • The IAM analyser is deliberately partial. No permission boundaries, no SCPs, no condition-key evaluation. It says so in its own header, and it would rather miss an admin than invent one.
  • Idle detection is structural, not usage-based. Nothing here reads CloudWatch, so "unused" means "attached to nothing", which is a claim the data actually supports.

If you only remember one thing to say about the code

The interesting decisions are all the same decision: put the judgement in code that can be tested, and leave the model to choose which tested thing to run. That is the tool boundary, the computed verdicts, the validated citations, the generated-never-applied remediation, and the hand-written answer key. Everything else follows from it.
